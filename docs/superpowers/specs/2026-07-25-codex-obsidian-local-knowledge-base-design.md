# Codex–Obsidian 本地知识库设计

## 1. 目标

在现有 Obsidian Vault 中建立一套由 Codex 自动维护的本地知识库。

人负责收集资料、提出问题和判断方向；Codex 负责读取原始资料、提炼知识、维护主题页面、建立交叉链接、发现矛盾并保持索引可用。Obsidian 作为知识浏览与人工编辑界面，Codex 与 Obsidian 通过共享同一个本地 Vault 文件夹协作，不依赖专用连接插件。

本方案采用 `llm-wiki` 的核心思想：知识不是在每次提问时从原始资料中临时重新拼接，而是被持续编译进一个可追溯、可演进的 Markdown Wiki。

## 2. 已确认的使用方式

- 维护模式：全自动。
- 触发方式：每次在 Codex 中打开此 Vault 并开始知识库任务时，执行一次增量同步。
- 原始资料：`Clippings/`，只读。
- LLM 维护范围：`topics/` 与 `system/`。
- 基础检索：原生 Markdown、Wiki 链接和内容索引。
- 初期不引入向量数据库、云端 RAG 或必需的 Obsidian 社区插件。
- 删除页面或大范围合并主题属于高影响操作，需要人工确认。

## 3. 方案选择

### 3.1 采用：原生 Markdown + 增量状态

Codex 直接读写 Vault，通过 `topics/index.md` 导航知识，通过 `system/source-state.json` 识别原始资料变化。

优点：

- 完全本地，结构透明。
- Markdown 文件可直接由 Obsidian、Codex 和普通编辑器读取。
- 没有额外服务和数据库的维护成本。
- 符合当前知识库规模，容易调试和迁移。

限制：

- 当笔记达到数百至数千篇后，纯索引检索可能变慢。
- 语义相近但措辞不同的内容，可能需要更强的搜索工具才能稳定发现。

### 3.2 后续升级：qmd 本地混合搜索

当笔记达到约 500–1000 篇，或 Codex 明显难以通过索引找到相关页面时，可以增加 qmd 的 BM25、向量检索和重排序能力。qmd 只增强检索层，不改变 Markdown 页面、目录结构或来源追踪规则。

### 3.3 暂不采用：完整 RAG/向量数据库

完整 RAG 架构会增加索引服务、数据库和同步逻辑，不符合当前的最小可用目标，也容易使系统重新依赖“查询时临时拼接”，弱化持久 Wiki 的价值。

## 4. 目录结构

```text
Obsidian Vault
├── AGENTS.md
├── Clippings/
│   └── assets/
├── topics/
│   ├── index.md
│   ├── concepts/
│   ├── entities/
│   ├── syntheses/
│   └── sources/
└── system/
    ├── ingest-log.md
    ├── source-state.json
    └── lint-report.md
```

### 4.1 `AGENTS.md`

Codex 的知识库维护规范。它定义可写范围、页面格式、增量导入流程、引用规则、冲突处理、安全边界和健康检查规则。

### 4.2 `Clippings/`

原始资料层，是事实追溯的来源。Codex 可以读取但不能修改、移动或删除其中的文件。图片和附件统一放在 `Clippings/assets/`。

### 4.3 `topics/`

由 Codex 维护的持久知识层：

- `index.md`：全库内容导航，每页包含链接和一句话说明。
- `concepts/`：概念、方法、理论和原则。
- `entities/`：人物、组织、项目、工具和其他命名实体。
- `syntheses/`：跨来源比较、综合判断、研究结论和值得长期保存的问答。
- `sources/`：每份原始资料的忠实提炼页。

### 4.4 `system/`

机器维护信息：

- `ingest-log.md`：追加式操作日志。
- `source-state.json`：原始资料的路径、内容哈希、处理状态、处理时间和关联来源页。
- `lint-report.md`：最近一次知识库健康检查结果。

## 5. 页面模型

Codex 生成的知识页面统一使用以下 Frontmatter：

```yaml
---
type: concept | entity | synthesis | source
status: seed | growing | mature | disputed
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources:
  - "[[原始资料文件名]]"
tags:
  - 标签
---
```

字段含义：

- `type`：页面职责。
- `status`：知识成熟度或争议状态。
- `created`：首次创建日期。
- `updated`：最近一次实质更新日期。
- `sources`：支撑页面内容的原始资料链接。
- `tags`：宽泛分类；具体关系主要使用 Wiki 链接表达。

概念页、实体页和综合页采用以下正文结构：

```markdown
# 页面标题

## 概述

说明页面讨论的对象和范围。

## 核心内容

呈现经过多来源整合的长期知识。

## 证据与来源

- 观点或事实。来源：[[原始资料]]

## 分歧与不确定性

记录资料冲突、适用条件、证据不足和待验证内容。

## 相关主题

- [[相关主题]]
```

来源页可以根据原文内容调整小节，但至少包含：

- 来源信息。
- 核心摘要。
- 关键论点或事实。
- 涉及的概念与实体。
- 与现有知识的关系。
- 需要进一步验证的问题。

## 6. 命名、链接与合并规则

- 文件名使用可读的中文名称或原始专名，不使用随机编号。
- 内部关系使用 Obsidian `[[Wiki 链接]]`。
- 每项重要事实或判断必须能追溯到来源页或原始资料。
- 相同概念有多个名称时，选择一个主页面，其他名称写入 `aliases`。
- 创建新页面前先检索现有索引和相关目录，避免同义重复。
- 标签保持扁平和少量复用，不用标签替代具体知识关系。
- 新资料与旧结论冲突时，不直接覆盖旧结论；同时记录双方证据，将页面标为 `disputed`。
- Codex 推导出的内容明确标注为“综合判断”，与来源直接陈述分开。
- 原始资料被移走时，知识页保留，并标注来源不可用。

## 7. 增量同步流程

每次开始 Codex 知识库任务时：

1. 读取 `AGENTS.md`。
2. 扫描 `Clippings/` 中支持的资料。
3. 通过规范化路径、文件大小、修改时间和内容哈希，与 `system/source-state.json` 比较。
4. 将资料识别为新增、已处理、已变更、缺失或失败待重试。
5. 逐篇处理新增、变更和失败待重试的资料。
6. 创建或更新对应的 `topics/sources/` 来源页。
7. 提取概念、实体、关系、证据和矛盾，合并进已有主题页。
8. 必要时创建新的概念页、实体页或综合页。
9. 更新 `topics/index.md` 和关联页面的 Wiki 链接。
10. 执行轻量健康检查。
11. 追加 `system/ingest-log.md`，最后更新资料状态。
12. 向用户显示简短同步报告，再处理用户当前提出的问题。

增量处理必须具备幂等性：资料没有变化时，重复运行不会重复创建页面、日志之外的重复内容或无意义地改写更新时间。

## 8. 处理状态

每份原始资料具有以下状态之一：

- `new`：尚未处理。
- `processing`：当前正在处理。
- `complete`：最近一次处理成功。
- `failed`：处理失败，并记录错误原因。
- `changed`：成功处理后原始内容又发生变化。
- `missing`：状态中存在记录，但原始文件已移走。

`source-state.json` 至少记录：

- 相对于 Vault 的文件路径。
- 内容哈希。
- 文件大小和修改时间。
- 当前状态。
- 最近处理时间。
- 对应的来源页。
- 最近错误信息（如有）。

## 9. 故障恢复与安全边界

- 单篇资料失败不会阻断其他资料同步。
- 失败项目在下一次同步时自动重试。
- 页面内容写入成功后，才能把资料标记为 `complete`。
- 原始资料消失时，只标记为 `missing`，不自动删除知识页。
- 检测到异常的大规模新增、变化或缺失时，暂停跨页面整合并请求人工确认。
- Codex 不修改、移动或删除 `Clippings/` 中的任何内容。
- Codex 的自动写入限定在 `topics/` 和 `system/`。
- 删除知识页、大范围合并主题或改变既有目录模型前，必须取得人工确认。
- 不确定内容标记为待验证，不作为确定事实写入。
- 自动同步结束后报告新增、更新、失败、冲突和需人工处理的项目。

“异常的大规模变化”定义为单次扫描中至少满足一项：

- 超过 20 个既有来源文件变为 `missing`。
- 超过现有已处理来源总数的 25% 同时发生变化或缺失。

当知识库中已处理来源少于 20 篇时，只使用“超过 20 个文件”的绝对阈值，避免初期少量正常变更频繁触发暂停。

## 10. 健康检查

每次同步后执行轻量检查：

- 失效的内部链接。
- 缺少来源支撑的事实性陈述。
- Frontmatter 缺失或格式错误。
- 重复或明显近义的页面。
- 没有入链或出链的孤立主题页。
- 新旧资料间的明显矛盾。

每累计成功处理 20 篇新增或变更资料后，执行一次深度检查：

- 全库跨页面一致性。
- 主题合并建议。
- 成熟度和争议状态是否合理。
- 索引覆盖是否完整。
- 重要知识缺口及建议补充的资料。

深度检查只提出删除和大范围合并建议，不自动执行高影响改动。

## 11. 日志格式

`system/ingest-log.md` 使用追加式记录，标题格式固定：

```markdown
## [YYYY-MM-DD HH:mm] ingest | 资料标题
## [YYYY-MM-DD HH:mm] lint | light
## [YYYY-MM-DD HH:mm] lint | deep
```

每条导入记录包含：

- 原始资料路径。
- 处理结果。
- 新建页面。
- 更新页面。
- 发现的冲突。
- 错误或待人工处理事项。

## 12. Obsidian 使用方式

- 文件浏览器用于查看 `topics/` 的知识结构。
- 反向链接和出链用于追踪主题关系。
- 图谱视图用于发现中心页面、孤立页面和知识簇。
- 属性视图用于查看页面类型、状态、日期和来源。
- 方案基础功能不依赖 Dataview 等社区插件；未来可将 Dataview 作为可选展示层。
- Codex 与 Obsidian 不需要通过 API 或插件连接；两者访问同一个 Vault 即完成协作。

## 13. 验收标准

实施完成后必须验证：

1. 在 `Clippings/` 新增一篇资料后，下一次 Codex 知识库任务会自动识别并处理。
2. 未改变资料时连续运行两次，不会生成重复页面或重复知识段落。
3. Codex 不会修改 `Clippings/` 中的文件。
4. 每项重要事实或判断可沿 Wiki 链接追溯到来源。
5. 新资料会更新相关既有主题，而不只是生成孤立摘要。
6. 单篇处理失败后能够在下次同步重试，并且不破坏其他知识页。
7. 原始资料被移走时，系统标记来源缺失但不删除已提炼知识。
8. Obsidian 可以直接展示链接、反向链接、属性和图谱关系。
9. 失效链接、元数据问题、孤立页面和明显矛盾会进入健康检查报告。
10. 基础方案在无云端服务、无额外 Obsidian 社区插件的条件下可用。

## 14. 实施范围

第一阶段包括：

- 创建 Codex 专用 `AGENTS.md`。
- 建立 `topics/` 和 `system/` 的目录及基础文件。
- 定义并实现增量状态、导入日志和健康检查工作流。
- 将现有 `CLAUDE.md` 中有效的知识库约定迁移到 Codex 规范。
- 使用现有 `Clippings/llm-wiki.md` 做首次端到端验证。

第一阶段不包括：

- 安装 qmd。
- 建立向量数据库或云端 RAG。
- 实时文件监听。
- 自动删除页面。
- 自动执行大范围主题合并。
- 强制安装 Obsidian 社区插件。
