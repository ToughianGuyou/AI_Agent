# 上下文工程

## 概述

上下文工程（Context Engineering）是 Agent 设计中最关键的环节——它决定了 Agent 在每个决策点能看到什么信息、以什么样的结构看到这些信息。上下文是 Agent 的"眼睛"，模型智力只是基础，**上下文的质量才是 Agent 能力的真正上限**。一个中等能力的模型配上精心组织的上下文，往往能胜过顶级模型在信息匮乏下的盲目摸索。

从 Harness 工程视角看，上下文工程是 Harness 中"上下文与工具"层面的核心实现。

## 核心内容

### Agent API 的上下文结构

每次调用 LLM 的上下文由五部分构成：

- **系统提示词**（System Prompt）：定义 Agent 身份、权限和行为准则，包含用户记忆和动态注入的环境状态
- **工具定义**（Tool Definitions）：声明可用工具的名称、功能描述和参数格式
- **用户消息**（User Messages）：终端用户输入，可能包含 RAG 检索结果
- **助手消息**（Assistant Messages）：模型之前的回复和工具调用请求
- **工具结果**（Tool Results）：工具执行结果，通过 `tool_call_id` 关联

消息列表就是上下文的地基。每次 API 调用都是无状态的，所有信息必须完整提供。

### KV Cache 与上下文效率

KV Cache 是 LLM 推理过程中复用历史计算结果的机制：相同前缀的 key-value 对不需要重新计算。三条核心结论：(1) 尽量保持系统提示词等静态前缀不变以最大化缓存命中；(2) 把动态内容追加到末尾而非插入前缀中间；(3) 工具定义可动态加载到上下文末尾而不破坏前缀缓存。

### 提示工程（Prompt Engineering）

系统提示词是 Agent 的"岗位说明书"。设计原则包括：流程化设计（按阶段组织指令）、明确边界条件（"做不到什么"比"能做什么"更重要）、用具体例子代替抽象规范。工具描述的质量直接决定 Agent 使用工具的准确性——当 Agent 频繁选错工具时，应优先检查工具描述而不是怀疑模型能力。

### 提示注入（Prompt Injection）攻防

外部不可信内容进入上下文时可能包含恶意指令。防御层次：输入清洗（标注来源、角色隔离）、结构化角色隔离（system/user/tool 严格区分）、上下文外复核（关键操作由独立机制审查）。

### Agent Skills 的按需加载

解决提示词无限膨胀的核心机制：把特定领域的操作流程写成 Skill 文档，Agent 只在需要时加载对应 Skill。Skill 用自然语言描述操作流程，通过通用工具执行，避免了为每个场景创建专用工具。选择 Skill + 通用执行器还是专用代码工具，取决于参数复杂度、变更频率和模型能力三个维度。

### Agent 状态栏

Agent 不感知执行环境和用户时间、工作状态的问题：通过状态栏向 Agent 实时注入环境信息（当前时间、工作目录、系统状态等），让 Agent 像人类一样"看到"自己所处的环境。

### 上下文压缩（Context Compression）

当上下文接近窗口上限时的策略：按语义重要性分层压缩——保留关键事实和决策，用结构化摘要替换冗长轨迹，对较早内容做更高压缩比。压缩的目标是在信息保真度和 token 消耗之间取得平衡。

## 证据与来源

[[深入理解 AI Agent]] 第 2 章系统阐述了上下文工程的完整框架，包括 API 结构、KV Cache 原理和所有子领域的设计方法。该章被作者称为"全书最关键的一章"。

## 分歧与不确定性

- 上下文压缩的"最优"策略高度依赖任务类型和模型特性，目前以工程经验为主
- Skills 按需加载的触发时机（何时加载、加载多少）仍缺乏系统性的设计指南
- 提示注入的防御尚无完美方案，各层防御的边际收益未量化
