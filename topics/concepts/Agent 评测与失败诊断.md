# Agent 评测与失败诊断

## 概述
Agent 评测必须覆盖结果、过程、成本、时间、权限和完整轨迹，不能只用最终答案准确率。

## 核心内容
- 失败诊断应定位第一个不可恢复错误，而不是只解释最后一步。
- 部署模拟可减少静态评测的选择偏差和测试识别。
- 长程与并发环境会暴露上下文饱和、记忆串扰、依赖和重排开销。
- 评测应区分真实环境、模拟环境、内部流量和厂商自评。

### 工具调用型与人机交互型两种评估范式

[[深入理解 AI Agent]] 第 6 章构建了三个层次的评估体系：

**评估环境**：工具调用型（Verifiers 框架，基于可执行标准验证，如测试是否通过）vs 人机交互型（τ-bench/τ²-bench，用另一个 LLM 模拟用户角色）。人机交互型评估的核心挑战是渐进式信息透露——真实用户很少一上来就清晰描述需求，Agent 需要通过主动提问澄清需求，这本身就是能力的重要体现。

**评分体系**：Rubric 四准则——(1) 分维度评分而非单一总分；(2) 每个维度有明确的可验证标准；(3) 幻觉检测为否决项（与质量正交——一个流畅但包含虚假事实的回答比简短准确的回答危害更大）；(4) 每条扣分点必须引用轨迹证据。

**评估驱动的决策**：评估体系的首要价值不是给当前系统打分，而是能快速跟上模型演进。区分"模型能力不足"和"Harness 设计缺陷"的关键手段是模型替换实验（固定 Harness 只换模型）和消融实验（关闭 Harness 某个组件）。

τ²-bench 相比 τ-bench 的核心增量：双控环境（用户模拟器也能操作共享环境）、更精确的任务规范与组合式任务生成。

### 三层轨迹验证

第 8 章提出评价一次运行的三层验证结构：底层结果验证器（测试结果、数据库状态，回答"是否真的办成"）、中间过程验证器（业务规则、权限、动作序列，回答"是否以允许的方式办成"）、上层质量验证器（LLM Rubric 评价语言与策略，回答"是否办得合适"）。越靠下的指标越依赖代码和环境真值。

## 证据与来源
[[AgentRx]] 提供轨迹诊断；[[Predicting model behavior before release by simulating deployment]] 连接评测与部署分布；[[CORPGEN]] 测量多任务负载退化。

## 分歧与不确定性
LLM judge、合成任务和厂商私有数据都可能形成系统性偏差。
